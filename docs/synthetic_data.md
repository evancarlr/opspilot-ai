# Synthetic onboarding dataset

Generated by `src/opspilot/generate_data.py` (`uv run python -m opspilot.generate_data`).
All data is synthetic. It describes customer onboarding at Relay Technologies, a
fictional B2B SaaS company selling the RelayOS warehouse fulfillment platform
(see [relay-business-context.md](relay-business-context.md)). Timestamps are UTC.

## Time frame

- Signups: 2025-10-01 to 2026-09-30 (12 months).
- Snapshot (`as_of`): 2026-10-01 00:00. Nothing after this time is observable.

## Tables (`data/synthetic/`)

| Table | Grain | Columns |
|---|---|---|
| `customers` | one row per account | `customer_id`, `signup_at`, `account_status` |
| `customer_attributes` | one row per account | `customer_id`, `segment`, `plan_tier`, `region`, `acquisition_channel` |
| `onboarding_events` | one row per journey event | `event_id`, `customer_id`, `stage`, `stage_order`, `event_type`, `event_timestamp`, `outcome` |
| `support_tickets` | one row per ticket | `ticket_id`, `customer_id`, `created_at`, `category`, `severity`, `resolved_at` (null = open at `as_of`) |

`dataset_metadata.json` holds the same definitions in machine-readable form.

## Onboarding stages

| Order | Stage | Done when |
|---|---|---|
| 1 | `warehouse_provisioning` | Account setup: RelayOS tenant created, warehouses, locations and users provisioned |
| 2 | `erp_integration` | ERP and storefront connectors live; initial inventory import and ongoing sync verified |
| 3 | `fulfillment_configuration` | Picking, packing, shipping and order-routing rules configured |
| 4 | `testing_validation` | Test orders run end to end; inventory and fulfillment results validated |
| 5 | `go_live` | Live orders processed in RelayOS |

Each stage has one `stage_started` event, zero or more `stage_progress`
events (`on_track`, or `blocked` once the stage has run more than 2x the
typical duration for the segment), then `stage_completed` or `stage_abandoned`.
Stages run strictly in order.

## Support ticket categories

| Category | Technical | Meaning |
|---|---|---|
| `erp_integration` | yes | ERP or storefront connector errors and mapping |
| `inventory_sync` | yes | Inventory import or sync mismatches |
| `fulfillment_rules` | yes | Picking, packing or order-routing rule issues |
| `shipping_carrier` | yes | Carrier accounts, labels and rate shopping |
| `platform_bug` | yes | Defects in RelayOS itself |
| `how_to` | no | Product usage questions |
| `user_access` | no | Logins, roles and permissions |
| `billing` | no | Invoices, plans and payments |
| `feature_request` | no | Requests for new capabilities |

Technical tickets are the ones that need engineering or solutions-engineering
time (`technical_ticket_categories` in the metadata).

## Success criteria and journey status

- **Completed**: a `go_live` `stage_completed` event exists (`account_status = active`).
- **On target**: completed within the segment target time-to-value from
  `signup_at`: SMB 21 days, Mid-Market 40, Enterprise 75.
- **Abandoned**: a `stage_abandoned` event exists (`account_status = churned`).
  Customer success records it 30 days after the last onboarding activity, so
  its timestamp is the flag date, not the moment the customer disengaged.
- **In progress**: neither of the above (`account_status = onboarding`).

### Right-censoring

The generator simulates each full journey and then drops everything after
`as_of`. A journey whose last activity is within 30 days of `as_of` cannot be
classified as abandoned yet, even if it will be. Analyses must treat in-progress
journeys as censored, not abandoned. For example, compute stage abandonment
only for stage entries with enough follow-up time.

## Ground truth (`data/evaluation/ground_truth.json`)

Describes the three planted operational problems: windows, affected segments,
mechanisms, and expected trends. It lives outside `data/synthetic/` on purpose.
**Never pass it, or anything under `data/evaluation/`, to an analysis or AI
agent.** It exists only to score their findings. `write_dataset` refuses to
write ground truth inside the analysis directory.

## Design decisions

- **Simulate, then truncate.** Censoring comes from the snapshot rather than
  from hand-placed rules, so in-progress journeys include real latent
  abandonments, as in production data.
- **Abandonment via an inactivity rule.** Active journeys log progress at least
  every 21 days, so the 30-day rule never misclassifies a slow but active
  journey.
- **Statistical, not universal, effects.** Lognormal stage durations, a
  per-customer pace factor, gamma-distributed ticket propensity, and partial
  application of each problem (for example, only 75% of affected Enterprise
  signups are slowed).
- **Confounding left in deliberately.** Enterprise delays (problem 1) make
  prolonged journeys more common in Enterprise, and Enterprise files more tickets
  anyway, so problem 3 must be assessed within segment.
- **Business context excludes the answers.** `relay-business-context.md` may
  be given to an analysis agent, so it names the metrics leadership watches
  but not the planted problems.
- **Independent tests.** Pattern tests measure effects from the tables like
  an analyst would, and do not read the ground truth or generator internals.
